Q: A Spring Batch job imports a 1 M-row CSV. Which design is right?
* Chunk-oriented step: FlatFileItemReader → ItemProcessor (validate) → JdbcBatchItemWriter, with commit-interval ~500–1000 and skip/retry policies
- Read the whole file into memory, then save each row individually
- A single @Transactional method for all rows
- A tasklet that loops with no commits
E: Chunks commit in batches, so a failure loses only one chunk, and the JobRepository allows restarting from the last committed chunk. Use skip limits for bad rows and partitioning for parallelism.

Q: Users report slow pages. Grafana shows API p95 latency spiking while CPU is normal. First suspect?

Q: Generating a 500,000-row Excel report in Spring without running out of memory:

- XSSFWorkbook with all rows loaded into a List first
- Build the Excel file in the browser from a JSON array of all rows
- Increase the heap to 64 GB
E: For PDFs use JasperReports or OpenPDF. Run long reports as an async job (Spring Batch or @Async with status polling). Stream the result to object storage, and stream DB rows with a fetch size or Stream<T> inside a read-only transaction.
Q: Why generate PO financial reports asynchronously instead of inside the HTTP request?
* Long reports would exceed gateway/HTTP timeouts and tie up request threads; an async job returns 202 + job id, and the client polls or is notified when the file is ready
- Async reports are always more accurate
- HTTP cannot return files
- Browsers block downloads larger than 1 MB
E: Add a per-PO rate limit, cache reports that don't change, and audit who downloaded which financial file.
